Bearcorp Threat Hunt
Your mission
Attackers spent five days inside Bearcorp, a fictional company with about 10,000 hosts.
Your team is tasked to find the attacker’s actions in the company's logs, identify the
compromised hosts, and build a dashboard that helps analysts investigate them.
1. How it works
Hundreds of attacker actions are hidden in Bearcorp's logs. Searching logs for signs of an
attacker is called threat hunting. You will:
●
●
●
Write detections: SQL queries that search the logs for signs of the attacker.
Use your detections to identify the compromised hosts, and report each attacker action
as a finding in findings.json.
Build a dashboard: a front-end where someone can run your detections and change
their settings.
2. Log sources
Your detections run against various logs. Each log is a table in bearcorp.db.
More details about the logs are in the Log reference tab.
3. Team roles
For creating detections and generating findings, it is recommended to split up the work into four
roles. Each role focuses on a particular set of logs.

4. Identity analyst auth, vpn, ldap, fw, flow
More details in the Team roles tab.

3. Moving to finding real threats
Once you get an idea of what working with the logs is like, and the workflow of working with an
agent, move onto the Team roles tab, and start working to find the real threats.
1. Find your role's table in the Team roles tab. It lists seven hunts, ordered from easy to
hard.
2. Start with hunt 1. Write a detection for it, then save the findings it returns into a
findings.json.
3. Move to the next hunt when your detection stops turning up new attacks, or whenever
you get stuck. Each hunt stands on its own, there are not any dependencies.
4. If you finish your hunts early, I recommend reviewing your findings and detections for
false positives, or helping your teammates. From my testing, AI gets pretty far, but has a
lot of false positives (which hurts your score).
Once you are ready, your team can begin to create the dashboard and incorporate the
detections that you have created.

Log sources at a glance
Log source Overview
DNS (dns) DNS queries and answers, including record type, response code, returned value, and TTL.
Web proxy (proxy) Web requests with domains, paths, status codes, byte counts, and user agents.
Host sensor (host) IP assignments, logins, process starts, network connections, DNS queries, and commands.
Network flow (flow) Internal connections with source and destination addresses, ports, byte counts, and duration.
Authentication (auth) SSO, VPN, SSH, RDP, WinRM, SMB, and Kerberos authentication events.
Firewall (fw) Outbound firewall allow and deny decisions.
VPN (vpn) VPN sessions with the user, source IP, duration, and upload and download totals.
USB (usb) USB device insert, copy, and remove events, including megabytes copied.
LDAP (ldap) Directory queries from each host, including the filter and number of returned entries.

How findings are scored
Files with the same team
id are merged, and the combined findings are compared with the
_
answer key. A finding is correct when it matches an attacker action on all five fields:
Field Match rule
category The exact category name
host The exact host name
user The same name, in any capitalization
process The same name, in any capitalization
timestamp Within 5 minutes of the action's first event, before or after
Duplicates are ignored. If you or a teammate report an attack that is already matched, or repeat
a finding exactly, the extra copy counts neither for nor against your team. Teammates can work
on overlapping attacks without losing points.
The metrics
Metric How it is calculated
Precision Correct findings ÷ findings submitted, not counting duplicates
Recall Correct findings ÷ all attacker actions in the logs
F1 score (overall) 2 × precision × recall ÷ (precision + recall)
